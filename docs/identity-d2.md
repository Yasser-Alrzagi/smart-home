# تسليم الدفعة الثانية D2 — الحسابات والصلاحيات والجلسات

**التاريخ: 5 سبتمبر 2026. الحالة: نُفّذت واختُبرت على النسخة المحلية. ليست إكمالاً لنظام السكن كله.**

اعتمد صاحب المشروع أن **مسؤول النظام فقط ينشئ الحسابات ويحدد الأدوار، دون تسجيل عام**. بُنيت الدفعة على تسليم D1، في فرع محلي `feat/identity-d2`، دون دفع إلى GitHub أو اتصال بقاعدة بيانات صاحب المشروع.

## 1. ما أصبح يعمل؟

1. **إنشاء أول مدير بأداة CLI آمنة** تطلب كلمة المرور دون إظهارها، وتمنع إنشاء مدير أول ثانٍ حتى مع محاولتين متزامنتين.
2. **إدارة الحسابات لمسؤول النظام فقط:** إنشاء وعرض وتعديل الدور والنشاط وإعادة تعيين كلمة المرور، مع صفحات وترتيب ثابت وحدود مدخلات.
3. **خدمة ذاتية ضيقة لجميع الأدوار:** عرض الحساب وتعديل username/email وتغيير كلمة المرور باستخدام الحالية. لا يستطيع المستخدم تعديل دوره أو نشاطه أو هاشه أو auth_version عبرها.
4. **جلسات مخزنة خادمياً:** خروج من الجلسة الحالية أو الكل أو جلسة يملكها المستخدم؛ لا يستطيع إبطال جلسة مستخدم آخر.
5. **إبطال فعلي عند تغير الأمان:** تغيير/إعادة تعيين الكلمة أو الدور أو النشاط يبطل جلسات الهدف؛ إعادة التفعيل لا تعيد التوكنات القديمة.
6. **عقد JWT صارم:** حقول إلزامية وجهة إصدار وجمهور ونوع وإصدار ومعرف جلسة؛ الدور المعتمد من قاعدة البيانات لا من ادعاء JWT.
7. **حماية محاولات الدخول المشتركة بين العمليات:** عدادات MariaDB ذرية ومستقلة عن rollback طلب الدخول، و429 مع Retry-After، دون الاعتماد على ذاكرة عامل واحد.
8. **سجل أحداث للهوية:** لا كلمات مرور أو توكنات أو قيم بريد/ملف شخصي في التفاصيل، ورفض تعديل/حذف الحدث عبر ORM.
9. **تعطيل بدل حذف الحساب:** لا مسار حذف مستخدم؛ خدمات ومستودع المستخدم يرفضان الحذف النهائي. تعطيل الطالب لا يمحو ملفه أو تاريخ حالاته.
10. **حماية المدير النشط والتزامن:** لا يستطيع المدير تعطيل/خفض دور نفسه؛ العمليات الإدارية تسلسَل بقفل قاعدة البيانات، ويُلغى الطلب المتعارض برسالة 409 آمنة.
11. **فحص `/ready`** لإصدار المخطط وقفل الإدارة وجداول الهوية الأساسية؛ `/health` يبقى فحص اتصال.
12. **استبدال python-jose بـPyJWT** وإزالة سلسلة اعتمادياته غير المستخدمة، مع تحديث القفل والتصدير.

الحسابات التي ينشئها المدير أو يعيد تعيين كلماتها تتطلب تغيير الكلمة قبل العمل العادي. أول مدير يختار كلمته بنفسه، فلا يُفرض عليه تغييرها فوراً.

## 2. نتائج التحقق الفعلية

| الفحص | النتيجة |
|---|---|
| Python 3.13.14، بيئة جديدة من الاعتماديات المقفلة | **404 ناجحة، صفر فشل، صفر تخطٍّ** |
| Python 3.12.14، بيئة جديدة مستقلة | **404 ناجحة، صفر فشل، صفر تخطٍّ** |
| دون قاعدة اختبار، مع وجود رابط تشغيل وهمي في البيئة | **241 ناجحة، 163 متخطّاة صراحةً**، صفر فشل |
| مصفوفة الأدوار التسعة عبر HTTP | السماح والمنع وفق السياسة المختارة |
| التزامن | إنشاء أول مدير متزامن، وتعطيل متبادل بين مديرين، وعداد دخول عبر ثمانية اتصالات |
| ترقية حساب D1 اصطناعي ثم الرجوع/إعادة الترقية | بقي الحساب وهاش كلمته محفوظين |
| دورة هجرة كاملة وفحص اختلافات المخطط | ناجحة |
| فحص Ruff وتوافق الاعتماديات | ناجحان |
| فحص 37 اعتماد تشغيل مقفلاً | **صفر تنبيهات معروفة وقت الفحص** |
| الحالة بعد الاختبارات | صفر صفوف أعمال/أحداث/جلسات تجريبية متبقية؛ صف القفل التقني 1 محفوظ |

ارتفع عدد الحالات من 297 في D1 إلى 404؛ الزيادة تشمل اختبارات سلوك جديدة وحالات إضافية للجداول والتوثيق. لا تُجمع نتيجتا نسختي Python على أنهما اختبارات مختلفة.

تغطية الأسطر 95.26%، والفروع 78.46%، والنسبة المركبة 93.78%. هذه نسب الكود الموجود، وليست نسبة اكتمال المنتج ولا ضماناً أمنياً.

يوجد تحذيران من توافق مكتبات الاختبارات Starlette/httpx/AnyIO؛ لم يفشل اختبار بسببهما. الاختبارات الحية كانت على Linux وMariaDB 11.8.6، وليس Windows/XAMPP أو بنية صاحب المشروع. CI مُحدّث في الملفات لكنه لم يُشغّل على GitHub لأن التغييرات لم تُدفع إليه.

## 3. أمثلة ما أثبتته الاختبارات

- الدور المزور داخل توكن موقّع بمفتاح المختبر لا يرفع الطالب إلى مدير؛ التفويض من DB.
- توكن صحيح التوقيع بلا جلسة مخزنة أو بحقوق قديمة/جلسة منتهية يُرفض.
- حذف exp أو iss أو aud أو jti أو ver، أو تغيير النوع إلى refresh، يُرفض.
- محاولات تمرير role/is_active/password_hash/auth_version من تحديث الملف الذاتي تُرفض.
- المستخدم لا يقرأ قائمة الحسابات أو سجل الأحداث، ولا يبطل جلسة مستخدم آخر.
- التوكنات السابقة تفشل بعد تغيير الكلمة أو إعادة تعيينها أو تغيير الدور أو التعطيل/إعادة التفعيل.
- إنشاء حساب مكرر يرجع 409 ولا يسجل إنشاءً ناجحاً وهمياً.
- فشل كتابة حدث التدقيق يُلغي إنشاء الحساب، فلا يحدث تغيير إداري غير مسجل في ذلك المسار.
- الخطأ المتزامن لا يترك تحديثاً جزئياً، ولا تؤدي محاولتا تعطيل متبادلتان إلى فقدان جميع المديرين النشطين.
- اختلاف حالة أحرف اسم مستخدم معروف لا يتجاوز عداده، وتغيير X-Forwarded-For لا يتجاوز حد المصدر داخل التطبيق.
- فشل الدخول يترك عداده وحدثه pseudonymous رغم تراجع معاملة الطلب.
- الأسرار لا تظهر في repr للنماذج أو إعدادات السر، ولا في رسالة خطأ تمرير كلمة مرور إلى CLI بالطريقة غير المدعومة.

هذه اختبارات آلية وظيفية وأمنية محددة، وليست اختبار اختراق شاملاً على شبكة حقيقية أو اختبار حمل إنتاجي.

## 4. تغيير قاعدة البيانات

الهجرة الجديدة: `d2a5c19f0b72` بعد `ca98ebed8d42`.

- إضافة `auth_version` و`must_change_password` إلى users.
- إضافة `auth_sessions` للجلسات والإبطال.
- إضافة `audit_events` للأحداث.
- إضافة `login_rate_buckets` لحدود المحاولات.
- إضافة `account_guard` وصف ثابت رقم 1 لتسلسل التهيئة والإدارة بأمان.

صار الإجمالي **26 جدولاً**. ملف الهجرة الأول بقي مطابقاً بالبايت لتسليم D1؛ لم نغيّر تاريخه لإرضاء النماذج الجديدة. اختباره يقارن بعقده المجمد، واختبارات المخطط الحي تقارن حصيلة الهجرات بالنماذج الحالية.

لا تُنفذ downgrade على بيانات تريد الاحتفاظ بها: الرجوع عن D2 يحذف جداول الجلسات والأحداث. MySQL/MariaDB DDL لا تلغيه معاملة عادية بالكامل عند تعثر الهجرة؛ راجع خطة الاستعادة والنسخ الاحتياطية قبل أي تطبيق خارج المختبر.

## 5. كيف تبدأ عندك؟

استخدم نسخة مستقلة للمراجعة أولاً، ثم اتبع README. باختصار:

```text
python -m pip install --require-hashes -r requirements.txt
```

راجع `.env`، وخاصة المفتاح والاتصال. **غيّر ACCESS_TOKEN_EXPIRE_MINUTES القديم من 1440 إلى 30**؛ المسموح الآن 1–60. ثم:

```text
alembic upgrade head
python -m tools.bootstrap_admin --username YOUR_ADMIN --email you@example.com
python main.py
```

- bootstrap لأول مدير فقط؛ إذا عندك مدير سابق فلا تُنشئ مديراً جديداً عبرها، بل سجّل دخول الحساب الموجود بعد الترقية.
- لا كلمة مرور افتراضية ولا حساب جاهز داخل ZIP، ولا `.env` حقيقي ضمن التسليم.
- توكنات D1 تتوقف عمداً؛ يلزم الدخول مجدداً.
- الواجهة المرئية لم تُبنَ بعد؛ يمكن تجربة APIs عبر Swagger محلياً مع DEBUG=True.
- الحساب القديم بكلمة bcrypt أطول من 72 بايت يحتاج إعادة تعيين مصرحاً بها. لا يوجد مسار استرجاع مجهول أو بريد تلقائي في D2.

المسارات، المصفوفة، وحدود المحاولات والاحتفاظ موثقة في [identity-policy.md](identity-policy.md).

## 6. الحدود والقرارات المتبقية

- إنشاء حساب بدور Student لا ينشئ ملف الطالب أو طلب السكن؛ هذا ضمن D3.
- الواجهة، المستندات، دورة قبول الطلب، التوزيع والتزامن في الغرف، الخدمات، الشكاوى، الغياب، وBFS/A* لم تُنفذ في D2.
- صلاحيات قرارات السكن/الخدمات لم تُمنح للأدوار بالافتراض؛ سنعتمدها عند بناء تلك الوظائف.
- MFA واسترجاع الحسابات وقائمة الكلمات الشائعة وTLS والنسخ الاحتياطي/الاستعادة وضبط التشغيل لا تعمل تلقائياً هنا.
- حدود الدخول تراعي المصدر وزوج الحساب/المصدر، وليست حصانة من هجمات موزعة. اضبطها لبيئة NAT الخاصة بالسكن.
- السجل ليس محصناً ضد DBA/SQL مباشر. قيّد صلاحيات DB والوصول التشغيلي. روابط CASCADE القديمة لم تُغير؛ الحذف النهائي محظور في واجهات وخدمات الحساب الحالية.
- مدة الاحتفاظ بالأحداث والجلسات وإجراءات محوها لا تزال تحتاج قراراً قبل النشر. لا حذف تلقائي لها الآن، وهذا ليس توصية بالاحتفاظ الدائم.
- أداة تنظيف عدادات الدخول المنتهية متاحة بمعاينة افتراضية و`--apply` للتطبيق، لكنها تحتاج جدولة من المشغل.
- فحص الاعتماديات بلا تنبيهات لا يساوي خلو النظام من كل الثغرات.

## 7. ملفات التسليم

- `smart-home-identity-d2.zip`: المصدر الكامل، ويشمل D1 وD2 والتوثيق والأدلة.
- `d2-on-d1.patch`: تعديلات D2 فقط، لمن طبّق تسليم D1 سابقاً.
- `d1-d2-from-original.patch`: التعديلات التراكمية من النسخة الأصلية المفحوصة `507615e`.

لا تُطبق الرقعتين معاً. استعمل `git apply --check` أولاً على نسخة مستقلة. لم ينشئ هذا العمل commit جديداً أو يدفع تغييرات إلى المستودع البعيد. التغيير المحلي السابق في `_offline_head.sql` حُفظ خارج الرقعتين.

**الخطوة التالية المقترحة: D3 — ملف الطالب وطلب السكن والمستندات، مع واجهة عربية أولية بعد تثبيت عقود API.**
