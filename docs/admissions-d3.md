## السياسة التي اعتمدها صاحب المشروع

- **شؤون الطلاب** تتحقق من الطلب والمستندات ثم تحيله.
- **إدارة السكن** تصدر قرار القبول/الرفض بعد اكتمال مراجعة شؤون الطلاب، أو تعيده للمراجعة مع السبب.
- **الهوية الوطنية وإفادة القيد إلزاميتان**. البطاقة الجامعية اختيارية، إلا إذا طلبتها شؤون الطلاب ضمن استكمال محدد.
- مسؤول النظام يدير الحسابات كما في D2، ولا يُمنح صلاحيات مراجعة السكن أو تنزيل المستندات بمجرد كونه مسؤول نظام.

## ما نُفّذ

### ملف الطالب

إنشاء وقراءة وتحديث الملف الذاتي: الاسم الكامل والجامعة والتخصص. لا يستطيع الطالب تمرير user_id أو academic_status أو housing_status أو أرقام النسخ لفرض قيمها من واجهة الإنشاء.

التحديث يتطلب `expected_version` ويُرفض عند تعارض النسخة. يُسمح بتعديل الملف قبل التقديم أو أثناء الاستكمال، ويُقفل أثناء المراجعة وبعد القبول. عند إعادة التقديم تُحفظ نسخة جديدة من البيانات في الطلب، ولا تتبدل بيانات طلب مقبول بتعديل لاحق لملف الطالب.

الحالة الابتدائية للملفات الجديدة `Applicant`، لا `Active`. القبول في D3 **ليس تخصيص غرفة**، ولا ينشئ RoomAssignment. بيانات الطلاب السابقين لا تُحوّل تلقائياً إلى متقدمين.

### دورة الطلب

```text
الطالب: مسودة → رفع المستندات → تقديم
شؤون الطلاب: تقديم → قيد المراجعة → جاهز للقرار
إدارة السكن: جاهز للقرار → مقبول أو مرفوض
```

مسارات إضافية مضبوطة:

- شؤون الطلاب: تقديم/قيد المراجعة → بانتظار المستندات، مع قائمة مطلوبة وسبب واضح.
- الطالب: استكمال المستندات/البيانات → إعادة التقديم؛ لا تجاوز للمراجعة السابقة.
- إدارة السكن: جاهز للقرار → قيد المراجعة، مع سبب؛ يزول اعتماد المراجعة السابق وتلزم إحالة جديدة.
- الرفض يتطلب سبباً. الحالات النهائية لا تُعاد كتابتها عبر الواجهات.
- يمكن إنشاء طلب جديد بعد رفض السابق. لا أكثر من طلب مفتوح/مقبول للطالب عبر الخدمات الحالية؛ التجديد السنوي وما بعد إنهاء الإقامة سياسة لاحقة.

كل كتابة على الطلب أو مستنداته تتطلب النسخة المتوقعة وتزيد `version`. الأقفال بترتيب ثابت للمستخدمين ثم الملف ثم الطلب، مع إعادة تحقق الجلسة والدور بعد القفل. لا تُرجع أخطاء التزامن نجاحاً وهمياً؛ قد ترجع 409 ويجب تحديث العرض قبل المحاولة.

### مستندات خاصة وليست روابط عامة

- PDF وJPEG وPNG فقط، افتراضياً حتى **5 MiB** لكل مستند. عدد الأنواع المتاحة ستة، وسجل واحد لكل نوع داخل الطلب.
- يتحقق الخادم من الامتداد والنوع الفعلي، وليس اسم الملف أو Content-Type فقط.
- تُرفض الملفات الفارغة والمزيفة وPDF المشفر أو المحتوي على إجراءات نشطة/مرفقات/نماذج تفاعلية.
- حد PDF عشرون صفحة؛ الصور حتى 12 مليون بكسل وغير متحركة. يعاد ترميز الصور لإزالة البيانات الوصفية والمحتوى الملحق مع مراعاة الاتجاه.
- التحليل في عملية فرعية بمهلة زمنية وبيئة دون أسرار التطبيق الممررة عبر متغيرات البيئة. على Linux توجد حدود CPU وذاكرة أيضاً؛ حد الذاكرة نفسه غير مفروض على Windows.
- هذه **ليست بيئة عزل أمنية كاملة ولا برنامج مكافحة فيروسات**. لا نثبت أصالة الهوية أو صحة المستند؛ المراجعة البشرية لازمة، والفحص ضد البرمجيات الضارة وتقوية العزل مطلوبان قبل استخدام بيانات فعلية.
- جسم الطلب محدد الحجم حتى دون Content-Length، قبل تحليل multipart. الطلبات تُخزّن مؤقتاً في ذاكرة محدودة؛ يلزم أيضاً ضبط التزامن والمهل في reverse proxy عند النشر.

تُحفظ الملفات كـ **MEDIUMBLOB داخل قاعدة البيانات**، لتكون الكتابة والإزالة وتحديث النسخة والسجل ضمن معاملة واحدة. لا تخزين للمستندات في static أو مسار تنزيل عام. لا يستخدم التطبيق `file_path` القديم لفتح ملف من القرص؛ سجلات المسارات القديمة تحتاج إعادة رفع متحققاً منها.

المحتوى مؤجل التحميل ولا يُضمّن في JSON للقوائم أو تفاصيل الطلب. التنزيل متاح لصاحب الطلب ولمراجعيه المصرح لهم فقط، ويرجع attachment وno-store وnosniff، باسم ثابت لا يتضمن اسم الملف الأصلي أو رقم هوية الطالب. يُفحص الحجم وSHA-256 عند التنزيل.

البيانات **ليست مشفرة على مستوى التطبيق داخل DB**؛ تشفير القرص والنسخ الاحتياطية وTLS وصلاحيات DB مسؤوليات تشغيل لازمة قبل النشر. خطط للسعة والنسخ: قاعدة البيانات ستتضمن محتويات المستندات، لا أسماءها فقط. اجعل max_allowed_packet مناسباً لحجم الملف؛ يوصى بـ16 MiB على الأقل للحد الافتراضي.

يمكن استبدال/إزالة المستند في المسودة أو أثناء طلب الاستكمال فقط. السجل يحفظ الإجراء، **ولا يحتفظ بكل نسخة سابقة من الملف المستبدل**. المستندات المقابلة لطلب مقبول لا تُعدّل من هذه الواجهات. مدة الاحتفاظ والأرشفة تبقى قرار تشغيل مطلوباً.

## الصلاحيات

| العملية | الطالب | شؤون الطلاب | إدارة السكن | بقية الأدوار، ومنها مسؤول النظام |
|---|---|---|---|---|
| ملف الطالب الذاتي | ملفه فقط | لا | لا | لا |
| مسودة طلب/رفع وإزالة ملفات | طلبه وفي الحالة المسموحة | لا | لا | لا |
| قراءة تفاصيل/تنزيل مستند | طلبه فقط | طلب مقدم، لا مسودة | طلب مقدم، لا مسودة | لا |
| بدء المراجعة/طلب مستندات/إحالة | لا | نعم | لا | لا |
| قبول/رفض/إعادة للمراجعة | لا | لا | بعد إحالة مكتملة فقط | لا |

الطالب لا يرى طلبات غيره في القوائم، حتى لو عرف المعرف. الإدارة لا تقرأ مسودات لم يقدّمها أصحابها. تعطيل الحساب يبطل وصول صاحبه وفق D2، ويمنع عمليات جديدة على طلبه حتى معالجة أهلية الحساب.

سجل `application_events` يحفظ الإجراءات والملاحظات والأدوار والنسخ بوقت UTC، وهو قابل للقراءة فقط عبر تفاصيل الطلب للمصرح لهم. تفاصيل سجل التدقيق العام تقتصر على المعرفات والانتقالات، لا محتوى الملف أو نص الملاحظات. حماية ORM ليست ضماناً ضد مسؤول DB أو SQL مباشر.

## الواجهة العربية

العنوان المحلي بعد التشغيل: **http://127.0.0.1:8000/app**.

- واجهة RTL متجاوبة وملفات CSS/JavaScript محلية، دون CDN أو خطوط خارجية.
- لوحة متابعة الطالب، الملف، قوائم الطلبات، المستندات، الملاحظات وسجل المراحل.
- أدوات شؤون الطلاب وإدارة السكن تظهر بحسب الدور والحالة، مع فرض السياسة في الخادم أيضاً.
- واجهة أولية لمسؤول النظام لإنشاء الحسابات وعرض حتى 50 حساباً وتفعيل/تعطيل الآخرين. الإدارة الموسعة متاحة عبر D2 APIs.
- تغيير كلمة المرور، عرض الجلسات، وإبطالها أو الخروج من الكل.
- لا تسجيل عام، ولا كلمة مرور افتراضية أو بيانات طالب حقيقية في التسليم.
- Bearer token في ذاكرة الصفحة فقط؛ لا localStorage أو sessionStorage أو cookies. تحديث الصفحة يتطلب الدخول مجدداً. الاستجابات القديمة لا تعيد بيانات جلسة منتهية، ونتائج الصفحات القديمة لا تستبدل الصفحة التي انتقل إليها المستخدم.
- قيم المستخدم والملاحظات تُعرض بواسطة DOM text، لا innerHTML. توجد سياسة CSP للواجهة، ويُمنع تضمينها من أصل مختلف عند DEBUG=False.

هذه واجهة أولية وليست تغطية لكل وظائف النظام أو لكل شاشات D2 الإدارية.

## واجهات D3

تحت `/api/v1`:

| الطريقة | المسار |
|---|---|
| GET | `/admissions/policy` |
| GET / POST / PATCH | `/students/me` |
| GET / POST | `/applications` |
| GET | `/applications/{id}` |
| POST | `/applications/{id}/submit` |
| POST | `/applications/{id}/review` |
| POST | `/applications/{id}/documents` |
| GET / DELETE | `/applications/{id}/documents/{document_id}` |

الرفع multipart: `file`, `document_type`, `expected_version`. الحذف يتطلب expected_version في query. بقية الأفعال تستعمل JSON مع النسخة المتوقعة. قرارات review: start / request_documents / complete / return_to_review / accept / reject، مع فرض الدور والحالة في الخادم.

## الهجرة والتشغيل

الهجرة الجديدة `d3b7a21c8f04` تتبع `d2a5c19f0b72`. الإجمالي 27 جدولاً. تضيف نسخ الطلب/الملف، البيانات المجمدة، حالة جاهز للقرار، بيانات المراجعة، محتوى المستندات وسجل مراحل الطلب.

قبل تغيير أي قاعدة تحتفظ ببيانات مهمة، خذ نسخة احتياطية وراجع الترقية. ثم في نسخة المشروع المحدثة وبيئة Python مناسبة:

```text
python -m pip install --require-hashes -r requirements.txt
alembic upgrade head
python main.py
```

إذا لم يوجد مدير سابق، استخدم أداة bootstrap الموثقة في README. أنشئ من حساب المدير حساب طالب وحساب شؤون طلاب وحساب إدارة سكن لتجربة الدورة. لا تجعل حساب المدير يفترض أدوار المراجعة تلقائياً.

- الترقية ترفض المستندات القديمة المكررة للنوع نفسه قبل بدء DDL، ولا تختار/تحذف إحداها تلقائياً.
- التراجع عن D3 يرفض وجود محتوى مستندات أو سجل/حالات/نسخ D3، ولا يمحوها لمجرد العودة للكود السابق.
- توليد SQL للتراجع دون اتصال معطل في D3، لأنه لا يستطيع التحقق من حواجز حماية البيانات.
- لا تعدّل رقم Alembic يدوياً، ولا تستعمل downgrade كبديل لخطة استعادة. MySQL DDL غير معاملاتي بالكامل.

## التحقق وإعادة الاختبار

اختبارات pytest تتطلب قاعدة TEST معزولة كما في D2؛ لا تستخدم قاعدة تشغيل. دورة الهجرات تتطلب قاعدة scratch مستقلة وRUN_MIGRATION_CYCLE=1. تنظيف الاختبارات يحذف بياناتها الاصطناعية وسجلاتها داخل تلك القواعد المخصصة.

```text
python -m pip install --require-hashes -r requirements-dev.txt
python -m tools.test_database
python -m pytest -q
python -m playwright install chromium
python -m tools.ui_smoke
```

اختبار المتصفح لا يُعدّ seed للإنتاج: يتحقق من TEST_DATABASE_URL، وينشئ مستخدمين اصطناعيين، ويشغّل خادماً محلياً مؤقتاً عند الحاجة، وينظف مستخدميه وطلباتهم عند الانتهاء. الصورة المرفقة ناتجة عن اختبار حقيقي، لا mockup مولداً بالذكاء الاصطناعي.

CI مهيأ لاختبارات Python 3.12/3.13 وChromium على 3.13. رُقيت أدوات Actions إلى إصدارات Node 24 مثبتة بمعرفات commits رسمية؛ تشغيل هذا التحديث على GitHub ينتظر رفع الفرع، ولم يحدث تلقائياً من جلسة العمل.
