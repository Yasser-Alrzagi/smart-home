# سياسة توزيع الغرف والنقل — D4

سكن بازرعة الطلابي · مرحلة D4 · تُطبّق فوق D1/D2/D3 دون أي تغيير في مخطط قاعدة البيانات.

## الملخص

D4 ينفّذ منتج السكن الفعلي فوق جداول `floors` / `apartments` / `rooms` /
`room_assignments` التي وُجدت منذ D1: إدارة البنية السكنية، تخصيص الغرفة للطالب
المقبول، نقل الطالب بين الغرف، إنهاء الإقامة، وفرض السعة ومنع تعارض التعيينات
تحت أقفال صفوف.

- **القبول ليس تسكيناً.** لا يُنشأ أي تعيين تلقائياً عند قبول طلب، ولا يتغير شيء
  في ملف الطالب عند القبول.
- **تسكين واحد نشط لكل طالب** في أي لحظة. التحويل يُنهي التعيين السابق (بوصف
  `Transferred` مع تاريخ نهاية) ويُنشئ تعييناً جديداً نشطاً؛ لا يُحذف أي سجل.
- **السعة مضمونة على مستوى المنطق** تحت قفل صف الغرفة: لا يمكن لتعيينين متزامنين
  تجاوز `rooms.capacity`، وأي محاولة على غرفة ممتلئة تُرفض بـ 422.
- **حالة الغرفة تُشتق من الإشغال** ما دامت ضمن حالات الإشغال (متاح، جزئي،
  مكتمل). حالات «صيانة» و«مغلق» قرار يدوي يمنع التسكين الجديد حتى يعيد المسؤول
  فتح الغرفة.

## الأدوار والصلاحيات

| الدور | البنية السكنية | التخصيص والنقل والإنهاء | الاستعلامات |
|---|---|---|---|
| Housing Administration | إنشاء مبنى/طابق وشقة وغرفة، تعديل السعة والحالة | نعم | نعم |
| Student | — | — | صفحة «غرفتي» تعرض تعيينه النشط وسجله فقط |
| Student Affairs / System Administrator / الضباط الآخرون | مرفوض (403) | مرفوض (403) | مرفوض (403) |

- أي عملية تتطلب `must_change_password=False`؛ الحسابات الجديدة يجب أن تغيّر
  كلمة المرور أولاً كما في D2.
- لا توجد واجهة عامة للقائمة أو التخصيص؛ كل نقاط النهاية تحت المصادقة.

## قواعد التخصيص

1. الطالب مؤهل فقط إذا كان لديه **طلب بوصف `Accepted`** (يراجَع في نفس المعاملة
   مع قفل صف الطالب).
2. حالة السكن `Suspended` أو `Terminated` تمنع التخصيص (409).
3. لا يجوز أن يكون للطالب تعيين نشط قائم (409).
4. الغرفة يجب أن تكون قابلة للتسكين: ليست `Maintenance` ولا `Closed` (409)،
   والإشغال الحالي أقل من السعة (422 عند الامتلاء).
5. عند أول تخصيص لطالب بوصف `Applicant`، تُنقل الحالة إلى `Active` ويُسجَّل
   صف في `student_status_history` (نوع `housing`: من `Applicant` إلى `Active`)
   مع اسم المسؤول وملاحظة عربية. إنهاء الإقامة لا يغيّر حالة السكن تلقائياً؛
   دورة حالة السكن (إيقاف، فصل، إجازة) عمل لاحق مستقل.
6. `assigned_by` يسجّل مسؤول الإسكان منفّذ العملية.

## قواعد النقل

- يُطبق فقط على تعيين نشط؛ ولا يُسمح بالنقل إلى نفس الغرفة (409).
- الغرفة الهدف تُفحص كما في التخصيص (صيانة/إغلاق 409، امتلاء 422).
- غرفتا المصدر والهدف تُقفلان معاً بترتيب `room_id` تصاعدياً لمنع الجمود،
  وتُعاد حالة كل منهما حسب الإشغال بعد النقل.
- التعيين القديم يصبح `Transferred` مع `end_date`؛ البنية لا تحذف سجلاً.

## قواعد الإنهاء

- يُقبل فقط للتعيين النشط؛ يصبح `Ended` مع `end_date`، ويُعاد اشتقاق حالة
  الغرفة، ويعود الطالب إلى قائمة «بانتظار غرفة» (لا تزال لديه طلبات مقبولة).
- لا حذف، لا تعديل تعيينات منتهية، لا «تراجع» — التصحيح عبر نهاية ثم تخصيص
  جديد، والسجل الكامل محفوظ.

## البنية السكنية

- `floors`: مفتاح فريد `(building_name, floor_number)`؛ `apartments`: فريد
  `(floor_id, apartment_number)`؛ `rooms`: رقم الغرفة فريد داخل الشقة (يفرضه
  المنطق؛ لا قيد قاعدة بيانات لهذا المعرّف، فأسماء مكررة تُرفض بـ 409).
- السعة من 1 إلى 10. تخفيض السعة تحت عدد المقيمين الحالي يُرفض (409).
- لا حذف للطوابق/الشقق/الغرف في هذه المرحلة؛ «الإغلاق» هو البديل المدعوم،
  و`RESTRICT` في المفاتيح الأجنبية يمنع الحذف أثناء وجود غرف/تعيينات.
- حالة «متاح» يُشتق منها جزئي/مكتمل تلقائياً حسب الإشغال؛ محاولة تعيين حالة
  إشغال يدوياً تُرفض بـ 422.

## واجهة API

المسارات تحت `/api/v1` والمصادقة `Authorization: Bearer <token>`.

| Method | Path | الوصول / الأثر |
|---|---|---|
| GET | `/housing/floors` | قائمة المباني/الطوابق |
| POST | `/housing/floors` | إضافة مبنى/طابق (201) |
| GET | `/housing/apartments?floor_id=` | قائمة الشقق |
| POST | `/housing/apartments` | إضافة شقة (201) |
| GET | `/housing/rooms?status=&building=&offset=&limit=` | الغرف مع الإشغال |
| POST | `/housing/rooms` | إضافة غرفة (201) |
| PATCH | `/housing/rooms/{room_id}` | رقم/سعة/حالة الغرفة |
| GET | `/housing/students/unassigned` | المقبولون بلا تعيين نشط |
| GET | `/housing/assignments?status=` | التعيينات (مقسمة) |
| POST | `/housing/assignments` | تخصيص غرفة (201) |
| POST | `/housing/assignments/{id}/transfer` | نقل (201) |
| POST | `/housing/assignments/{id}/end` | إنهاء الإقامة |
| GET | `/housing/me` | الطالب: تعيينه النشط وسجله |

`/ready` يتضمن الآن فحص جداول `floors`, `apartments`, `rooms`,
`room_assignments` إلى جانب فحوصات الجلسة والطلبات.

## التدقيق

كل عملية تُسجَّل في `audit_events` بأفعال:
`housing.floor_create`, `housing.apartment_create`, `housing.room_create`,
`housing.room_update`, `housing.allocate`, `housing.transfer`,
`housing.end_assignment`.

التفاصيل المسموحة **معرّفات وأرقام فقط** (`floor_id`, `apartment_id`,
`room_id`, `assignment_id`, `from_room_id`, `to_room_id`, `occupancy`,
`capacity`, `room_status`, `student_id`): لا أسماء، لا بيانات ملفات، لا
قيم خاصة. `record_event` يرفض أي مفتاح خارج القائمة المسموحة.

## ما لا يفعله D4

- لا تخصيص آلي أو دفعات جماعية أو «أولوية» (الطلاب الجدد/القدامى).
- لا فصل حسب الجنس، ولا توزيع حسب الكلية/التخصص، ولا قواعد شراكة غرفة.
- لا «حجز» أو إشعارات؛ جدول `notifications` بلا خدمة بعد.
- لا ربط بجدول الصيانة/الشكاوى؛ الملاحظات تُسجَّل في التدقيق فقط.
- لا حذف تعيينات، لا تغيير للحالة السكنية عند الإنهاء.
- لا واجهة للطلاب لطلب غرفة معينة — طلب السكن عبر دور شؤون الطلاب/إدارة
  السكن كما في D3.

```text
TEST_DATABASE_URL=... python -m pytest tests/unit/test_housing_rules.py tests/integration/test_housing_d4.py -q
```

- `tests/unit/test_housing_rules.py`: قواعد اشتقاق حالة الغرفة النقية.
- `tests/integration/test_housing_d4.py`: دورة كاملة عبر HTTP وقاعدة حقيقية —
  البنية والتكرارات، شروط القبول، السعة واشتقاق الحالة، الصيانة/الإغلاق،
  التعليق، النقل (نجاح/تصادم)، الإنهاء وإعادة الأهلية، المصفوفة:
  أدوار 403/401، التنافس الفعلي `capacity=1` بطلابين متوازيين (تعيين واحد
  فقط ينجح)، سجل التدقيق، ورؤية الطالب لسكنه فقط.
- لا هجرة جديدة؛ `SCHEMA_HEAD` يبقى `d3b7a21c8f04`.
